# Plan 2030 — Roadmap de Correcciones Críticas para YSH

> Generado desde code review experto (2026-08-31)
> Priorizado por riesgo: dinero → auth → seguridad → arquitectura

---

## CRÍTICOS — Dinero + Auth (hacer primero)

### C1. Wallet Race Condition — Double Spend

**Problema:** `send_gift`, `stake`, `claim_staking_rewards`, `auto_process_payouts`, y admin `adjust_balance` no usan `wallet_lock`. Solo usan `write_lock` que serializa TODAS las escrituras pero no garantiza atomicidad read-modify-write del balance.

**Riesgo:** Dos operaciones leen el mismo balance antes de que una escriba → ambas pasan la validación de fondos → double spend.

**Fix:**
- Mover `wallet_lock` a ser usado por TODA operación que modifique balance:
  - `deposit` ✅ (ya lo usa)
  - `withdraw` ✅ (ya lo usa)
  - `transfer` ✅ (ya lo usa)
  - `send_gift` ❌ → agregar `wallet_lock`
  - `stake` ❌ → agregar `wallet_lock`
  - `claim_staking_rewards` ❌ → agregar `wallet_lock`
  - `auto_process_payouts` ❌ → agregar `wallet_lock`
  - `admin_adjust_balance` ❌ → agregar `wallet_lock`
- Alternativa: un solo `balance_lock` que cubra todas las operaciones de wallet

**Archivo:** `src/db.rs`

---

### C2. Sin Revocación de Sesiones

**Problema:** `AuthUser::from_request_parts` solo valida JWT contra `YSH_JWT_SECRET` env var. Nunca consulta el `session_cache`. Logout, ban, shadow-ban no invalidan tokens emitidos.

**Riesgo:** Un usuario baneado sigue con acceso hasta que su JWT expire (24h). Logout no hace nada real. Refresh token reutilizable 30 días sin rotación.

**Fix:**
1. Agregar `jti` (JWT ID) o `token_version` a los claims del JWT
2. En `AuthUser::from_request_parts`, validar contra `session_cache`:
   - ¿Existe el token?
   - ¿No ha sido revocado?
   - ¿El user no está baneado?
3. Implementar refresh token rotation:
   - Cada uso de refresh token genera uno nuevo y revoca el anterior
   - Almacén server-side de refresh tokens válidos
4. En logout: revocar access + refresh tokens
5. En ban/shadow-ban: revocar todos los tokens del usuario

**Archivos:** `src/auth/jwt.rs`, `src/auth/handlers.rs`, `src/auth/refresh.rs`

---

### C3. JWT Secret Divergente

**Problema:** Se crean tokens con `state.secure_jwt_secret` (de config) pero se validan con `std::env::var("YSH_JWT_SECRET")`. Si divergen, todos los tokens son rechazados.

**Riesgo:** Auth completamente rota silenciosamente.

**Fix:**
1. Usar una sola fuente de verdad para el secret
2. Validar en startup que el secret existe y tiene >= 32 bytes
3. Pasar el secret via `AppState` y usarlo en `AuthUser` en vez de leer env var directamente

**Archivos:** `src/auth/jwt.rs`, `src/main.rs`, `src/config/loader.rs`

---

### C4. Secrets en .env en Working Tree

**Problema:** `.env` contiene JWT_SECRET, ENCRYPTION_KEY, DB_PASSWORD, y password de Grafana en texto plano en el directorio del proyecto.

**Riesgo:** Leak de credenciales si alguien hace `git add -f`, CI artifact, o backup sin filtrar.

**Fix:**
1. Rotar todos los secrets inmediatamente
2. Mover `.env` fuera del repo (ej: `~/.config/ysh/.env`)
3. Asegurar `.gitignore` excluya `*.env` (ya lo hace, pero verificar)
4. Usar secret manager en producción (Vault, AWS Secrets Manager, etc.)

**Archivos:** `.env`, `.gitignore`, `docker-compose.yml`

## ALTOS — Seguridad

### H1. IP Spoofing — Rate Limiting Bypass

**Problema:** `extract_client_ip` confía en `X-Forwarded-For` / `X-Real-IP` sin validar contra `trusted_proxies`. Un atacante puede falsificar cualquier IP.

**Riesgo:** Rate limiting, DDoS protection, e IP blocklist se bypasean trivialmente.

**Fix:**
1. Implementar validación de `trusted_proxies` en `extract_client_ip`
2. Si no hay proxy configurado, usar solo el IP de la conexión real
3. Configurar `trusted_proxies` en producción

**Archivo:** `src/middleware/ddos_protection.rs`

---

### H2. /encrypt y /decrypt son Oráculos

**Problema:** Cualquier usuario autenticado puede cifrar/descifrar datos con la key simétrica del servidor (`YSH_ENCRYPTION_KEY`). Efectivamente expone un crypto oracle.

**Riesgo:** Un atacante puede usar el oráculo para descifrar datos cifrados por el sistema, o cifrar payloads maliciosos.

**Fix:**
1. Eliminar los endpoints `/encrypt` y `/decrypt` (son demo, no production-ready)
2. O: implementar per-user KEKs (Key Encryption Keys) en vez de la key del servidor
3. Validar que la key tiene exactamente 32 bytes (actualmente hace truncation silenciosa)

**Archivo:** `src/auth/handlers.rs`

---

### H3. WsGuard es Dead Code

**Problema:** `WsGuard` tiene todos los métodos marcados `#[allow(dead_code)]`. No se valida en el handler `/ws`. No hay:
- Límite de conexiones por usuario
- Rate limit de mensajes
- Heartbeat timeout
- Max message size

**Riesgo:** Un atacante puede abrir conexiones WS ilimitadas o inundar mensajes.

**Fix:**
1. Integrar `WsGuard` en `ws_upgrade_handler`
2. Validar: max conexiones por user (config: 3), heartbeat, rate limit
3. Mover token de query param a header (evitar tokens en URLs/logs)

**Archivos:** `src/ws/guard.rs`, `src/server.rs`

---

### H4. KYC Auto-Escalation

**Problema:** `submit_kyc` permite al usuario setear su propio `kyc_level`incrementándolo de 1 en 1. No hay verificación de identidad real.

**Riesgo:** Un usuario puede alcanzar "fully_verified" (nivel 3) sin verificación, evadiendo límites financieros.

**Fix:**
1. Requerir documentación/upload para niveles 2+
2. Requerir aprobación admin para nivel 3
3. O al menos: rate limit estricto + auditoría

**Archivo:** `src/auth/kyc.rs`

---

### H5. Circuit Breaker No Funciona

**Problema:** El circuit breaker nunca llama `record_failure()` en errores. Solo se invoca en `main.rs` durante probes de startup. Está placement after rate limiting (no protege upstream).

**Riesgo:** Falsa sensación de protección contra cascada de fallos.

**Fix:**
1. Agregar `record_failure()` en respuestas 5xx y timeouts
2. Mover circuit breaker antes de rate limiting (innermost → outermost)
3. O eliminar si no se va a implementar correctamente

**Archivo:** `src/middleware/circuit_breaker.rs`

## MEDIUM — Arquitectura + Calidad

### M1. db.rs God Object (5,279 líneas)

**Problema:** Un solo struct `Database` con ~150 métodos cubriendo todos los dominios: users, wallet, moments, chat, calls, payouts, staking, analytics, moderation, i18n, notifications.

**Fix:** Refactorizar en módulos de dominio:
```
src/db/
├── mod.rs              # Database base + conexiones
├── users.rs            # CRUD de usuarios
├── wallet.rs           # Balance, transacciones
├── moments.rs          # Feed, posts, likes
├── chat.rs             # Sesiones, mensajes
├── calls.rs            # WebRTC records
├── staking.rs          # Posiciones, rewards
├── moderation.rs       # Reports, flags, bans
├── notifications.rs    # Notificaciones
├── analytics.rs        # Métricas, snapshots
├── i18n.rs             # Traducciones
└── migrations.rs       # Migraciones de schema
```

---

### M2. Actores Decorativos (ractor)

**Problema:** 10 actores spawneados pero la mayoría solo loguean. `CryptoActor` genera key random en startup y nunca la usa. `SessionSupervisor` cuenta sesiones pero nunca enforced el límite. Solo `JobsActor` hace trabajo real.

**Fix:**
1. Evaluar si ractor es necesario o si se puede reemplazar con `tokio::spawn` + `tokio::sync`
2. Si se mantiene: implementar la lógica real en cada actor
3. Eliminar startup probes que ejecutan side effects reales

**Archivos:** `src/actors/`

---

### M3. Error Handling — Leakage de Internals

**Problema:** Casi todos los handlers hacen `.map_err(|e| (StatusCode::INTERNAL_SERVER_ERROR, e.to_string()))` — expone paths de archivos, errores de DB, y internals al cliente.

**Fix:**
1. Crear un `AppError` enum con variantes públicas
2. Mapear errores internos a mensajes genéricos
3. Logear el error real internamente, devolver mensaje seguro al cliente

**Archivos:** todos los `src/api/*.rs`

---

### M4. `let _ =` Silenciando Efectos Secundarios

**Problema:** Decenas de `let _ = state.db.create_receipt(...)` / `let _ = actor.send_message(...)` — side effects críticos fallan silenciosamente.

**Fix:**
1. Para receipts y transacciones: propagar error o logear con nivel WARN
2. Para notificaciones: OK ignorar, pero logear
3. Para actor messages: estructurar con retry o dead letter queue

**Archivos:** `src/api/wallet.rs`, `src/api/gift.rs`, `src/api/staking.rs`

---

### M5. DB Encryption At-Rest es Dead Code

**Problema:** `db_encryption.enabled` se carga en config pero `main()` siempre abre `Database::new(&db_path)` en plaintext.

**Fix:** Implementar la apertura condicional con `new_encrypted` cuando `db_encryption.enabled == true`.

**Archivo:** `src/main.rs`, `src/db.rs`

---

### M6. JSON-as-Column = Full Table Scans

**Problema:** Todas las entidades se serializan como JSON strings en redb. Todas las queries son `t.iter()` filtrando en Rust. O(N) en cada query.

**Fix (largo plazo):**
1. Evaluar migración a SQLite (ya tenemos `rusqlite` como dependencia potencial)
2. O: crear índices secundarios en sled para campos de búsqueda frecuentes
3. Implementar cursor-based pagination en vez de offset

---

### M7. Config Dice X pero Código Hace Y

**Campos cargados pero no wirados:**
- `workers` (server) — nunca se usa
- `supervision.*` strategies — nunca se aplican
- `backpressure.*` channel sizes — nunca se crean canales
- `CorsConfig.allowed_methods` — CORS hardcodea sus propios methods
- `database.max_connections` — no hay connection pool (redb es embedded)
- `tls.*` — TLS no está implementado (solo configurado)

**Fix:** O implementar cada feature o eliminar la config muerta.

---

## BAJO — Cleanup

### L1. Startup Smoke Tests en main()

**Problema:** `main()` ejecuta probes de startup que hacen side effects reales: encrypt con key propia, send email a `test@ysh.app`, key agreement consigo mismo.

**Fix:** Eliminar o mover a un feature flag `--smoke-test`.

**Archivo:** `src/main.rs`

---

### L2. Doble Apertura de Redb

**Problema:** `compact` y `integrity check` abren `RedbDatabase::create` mientras el primario está abierto.

**Fix:** Coordinar acceso o usar APIs de redb para compactación in-process.

**Archivo:** `src/db.rs`

---

### L3. Token en Query String del WebSocket

**Problema:** El JWT se pasa como `?token=` en la URL del WebSocket — aparece en logs, proxies, y referrers.

**Fix:** Usar subprotocol o primer mensaje autenticado en vez de query param.

**Archivos:** `src/server.rs`, `frontend/src/api.rs`
